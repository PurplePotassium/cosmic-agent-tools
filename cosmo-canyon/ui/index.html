🕹 Three ways to drive the loop

All three read/write the same control/ plane and delegate every gate/commit to the same bookkeep.mjs — the deterministic rails never move; only who runs the ticks differs. Full playbook: AGENTS.md › “Three ways to drive it” + docs/DRIVE.md.

A · Claude Code, present — the default (“Drive Cosmo Canyon”). Recommended. In a Claude Code chat say Drive Cosmo Canyon to do X; the agent orchestrates with its own judgment + vision, spawning Agent subagents per bead. Most adaptive — you watch, steer, and stop it in chat. No external process, no claude -p.
B · In-app Workflow — desktop app, hands-off. From a desktop chat session launch the dynamic Workflow:
Workflow({scriptPath:"cosmo-canyon/orchestrator/cc-loop.workflow.js", args:{ticks:1, noPlanner:true}})
The Workflow script hosts the loop; each tick is a spawned agent (sense = haiku, work = sonnet, planner = opus), visible live in the app’s tasks pane. Runs only while the app/session is alive. Stop: set control/.paused or TaskStop the Workflow.
C · Detached supervisor — unattended / overnight, last resort. Click ▶ Start loop below — or POST /api/cosmocanyon/start, or CLI node orchestrator/supervisor.mjs. Spawns a detached supervisor.mjs running a per-tick claude -p. It is an invisible headless loop → the LOUD banner flags it while alive; ⏹ Stop loop (or control/.paused) halts it.

🧠 Worker engine

Check the models the orchestrator is allowed to use — it picks one per task (logic→agy, feel/visual→sonnet, hard/structural→opus), limited to your set (falls back to the next-best checked). Feel/visual needs a Claude model (agy is preview-blind). Agy auto-cools-down on a Gemini quota wall.

⚙ Concurrency & runtime —

How the loop runs — change while stopped. Serial = one bead at a time (safest, byte-for-byte). Parallel = up to N isolated-worktree workers with a single-committer merge.
